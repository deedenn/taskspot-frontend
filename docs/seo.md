# Главная и публичные SEO-страницы

## Содержание

Каталог `src/components/PublicPages/content.js` содержит 14 русскоязычных страниц:
два каталога, шесть рабочих сценариев, три статьи и три страницы шаблонов.
Тексты и файлы хранятся в репозитории. API, внешние изображения, новые зависимости,
секреты и переменные окружения для их генерации не нужны.
Используется локальный PNG `/brand/taskspot-logo.png` с исходными пропорциями.
Канонический домен: `https://taskspot.ru`.

| Маршрут | Содержание |
| --- | --- |
| `/solutions/` | Каталог рабочих сценариев |
| `/solutions/owner/` | Владелец малого бизнеса |
| `/solutions/department/` | Руководитель отдела |
| `/solutions/production/` | Организационные поручения на производстве |
| `/solutions/agencies/` | Брифы и внутренняя проверка в агентстве |
| `/solutions/retail/` | Организационные задачи розничных точек |
| `/solutions/remote/` | Асинхронная работа удалённой команды |
| `/resources/` | Статьи и шаблоны |
| `/resources/delegation/` | Постановка проверяемого поручения |
| `/resources/acceptance/` | Приёмка результата и доработка |
| `/resources/overdue-review/` | Разбор просроченных поручений |
| `/resources/task-register/` | Реестр поручений CSV |
| `/resources/weekly-review/` | Еженедельный обзор Markdown |
| `/resources/shift-checklist/` | Печатный HTML-бланк передачи смены |

Реальные файлы генерируются в `/resources/downloads/`:

- `task-register.csv`: UTF-8 BOM, запятая, поля в кавычках, строки CRLF,
  пример и пустая строка. Это самостоятельная таблица, не формат импорта в Taskspot.
- `weekly-review.md`: редактируемые таблицы повестки, решений и следующих действий.
- `shift-checklist.html`: автономный бланк с полями и стилями печати A4,
  без скриптов и внешних ресурсов. Не заменяет обязательные журналы и регламенты.

Примеры не выдаются за клиентские кейсы. Статистика, отзывы, рейтинги и
неподдерживаемые интеграции в материалы не добавлены.

## Интеграция и рендеринг

В `App.jsx` уже подключён ленивый default-экспорт `PublicPage` для
`/solutions/*` и `/resources/*` вне проверки авторизации. Компонент разрешает
только известные маршруты каталога; для неизвестного пути показывает страницу
«Страница не найдена». Список известных адресов экспортируется как `PUBLIC_ROUTES`.
Добавление записи в каталог не требует отдельного маршрута React Router.

`renderer.js` используется и React-компонентом, и статическим генератором.
Он принимает путь, а не произвольный HTML. Значения экранируются для HTML,
JSON-LD защищён от досрочного закрытия `script`. Параметры URL, пользовательские
данные и API-ответы не вставляются в разметку. Компонент обновляет метаданные
и восстанавливает предыдущие теги при размонтировании. CSS ограничен
классами `.public-pages`; навигация и сетки имеют мобильные варианты.

Главная `/` получает build-time HTML-shell через `scripts/landing-shell.js`.
До загрузки React в документе уже доступны единственный H1, описание продукта,
внутренние ссылки, тарифы и FAQ. Интерактивное приложение заменяет shell после
загрузки, поэтому маршрутизация и авторизация продолжают работать как раньше.
Тексты первого экрана, FAQ и тарифы для shell и React-компонента берутся из
`src/components/LandingPage/landingContent.js`. Метаданные главной содержат
description, canonical, robots, Open Graph, Twitter Card и JSON-LD
`SoftwareApplication` с предложениями тарифов.

Обычные ссылки `<a>` открывают самостоятельные HTML-документы. Плагин
`scripts/public-pages/plugin.js` при сборке создаёт для каждого известного
маршрута `index.html`, общий `/assets/public-pages.css`, три файла шаблонов,
`sitemap.xml` и `robots.txt`. В исходном HTML уже есть весь текст, навигация,
скачивание, title, description, canonical, Open Graph и JSON-LD. Исполняемого
JavaScript на статических страницах нет: единственный `script` содержит JSON-LD.
SPA-бандл не загружается. Основной `index.html` приложения не заменяется.

В dev-режиме плагин отдаёт те же документы, перенаправляет известные адреса
без завершающего `/` и с `/index.html` на канонические, возвращает HTTP 404
для неизвестных публичных адресов и отсутствующих файлов. Клиентский экран
ошибки сам по себе не меняет HTTP-статус: в production это обязанность веб-сервера.

## Сборка

Из каталога `frontend` используется штатная команда, в том числе на Timeweb:

```sh
npm run build
```

Дополнительный `--configLoader runner` не требуется. `vite.config.js` задаёт
абсолютный `root` относительно своего файла. Плагин получает путь к CSS из
`config.root` в `configResolved`, поэтому временное расположение собранного
Vite-конфига не влияет на чтение CSS. Публикуется содержимое `dist` целиком,
включая каталоги `solutions`, `resources`, `assets`, `brand` и SEO-файлы.
Значение Vite `base` должно оставаться `/`: публичные ссылки адресованы корню.

## Настройка веб-сервера

Пример директив внутри существующего блока nginx `server` находится в
`docs/nginx-seo.conf`. Это пример конфигурации, а не выполненное изменение
production. Путь `root` необходимо сопоставить с фактическим каталогом `dist`;
настройки TLS, домена и API остаются в существующей конфигурации хостинга.
Не добавляйте дублирующиеся `location`: согласуйте пример с текущими правилами.

Физические файлы и индексы каталогов обслуживаются раньше SPA fallback.
Неизвестные `/solutions/…`, `/resources/…` и отсутствующие скачивания должны
возвращать HTTP 404, а не основной HTML со статусом 200. Нельзя переопределять
эти ошибки глобальным `error_page 404 /index.html` или аналогичным SPA-правилом.
Алиасы `/index.html` и адреса каталогов без `/` перенаправляются на канонический
адрес с сохранением query string.

Для скачиваний пример задаёт MIME-типы, `Content-Disposition: attachment`
и `X-Robots-Tag: noindex`. В печатном HTML также есть `meta robots=noindex`.
В sitemap включены главная и 14 страниц каталога, без скачиваний, приватных
страниц и вымышленных дат обновления. Robots ограничивает обход app/API/auth-путей,
но не заменяет авторизацию и не гарантирует удаление адресов из поискового индекса.

## Проверки

```sh
node --test scripts/landing-shell.test.js
node --test scripts/public-pages/public-pages.test.js
npm test
npm run lint
npm run build
```

Тест landing-shell проверяет статический H1, тарифы, FAQ, внутренние ссылки,
сохранение SPA entry и совпадение основных метаданных с общей контентной моделью.
Остальные Node-тесты проверяют каталог, уникальность метаданных, разрешение маршрутов,
экранирование, полноту статических документов, внутренние ссылки и якоря,
содержимое скачиваний, sitemap/robots, Vite-хуки и dev middleware.
`PublicPage.test.jsx` проверяет React-рендеринг, переходы, обновление и
восстановление метаданных, скачивание без авторизации и неизвестный маршрут.
Для Node-набора дополнительных зависимостей не нужно. Остальные команды
требуют уже объявленных devDependencies; ограниченное локальное окружение
может не содержать ESLint или не разрешать запись временного Vite-конфига.

После применения nginx-примера администратор проверяет конфигурацию через
`nginx -t` и HTTP-ответы известных страниц, алиасов, неизвестных адресов и
скачиваний. Сам nginx в рамках этой разработки не перенастраивался.

Новая главная визуально проверена в браузере на desktop и мобильном viewport:
первый экран, продуктовые сцены, сетка возможностей и тарифы не имеют заметного
горизонтального переполнения. Для отдельного production QA по-прежнему нужно
открыть каталоги, статью, сценарий и шаблон с отключённым JavaScript, проверить
клавиатурный фокус, скачивание и печатный бланк.
